# MQTT Message Contract

**Status:** Authoritative for all components from Phase 1 onward.
**Contract version:** `1` (2026-10-27)
**Applies to:** ESP32-S3 firmware, Python device simulator, FastAPI backend, tests, dashboard (indirectly, through the backend).

Nothing except the broker exists yet. The simulator, backend and firmware MUST implement this document before integration. If an implementation disagrees with this document, this document wins until it is formally revised.

> The examples in the original project brief are illustrative. This document defines the actual validated schema.

---

## 1. Scope and authority

This contract defines:

- topic names and direction of travel,
- required and optional JSON fields,
- units, ranges and types used for validation,
- quality-of-service (QoS) and retained-message behaviour,
- command acknowledgement, timeout and duplicate handling,
- offline buffering and de-duplication rules,
- what "relay state" means for a solid-state relay without feedback contacts,
- the safety rules every publisher must respect.

**Guiding rule:** the MQTT broker is transport only. No safety decision may depend on the broker, the backend, the dashboard or the internet. The device enforces protection locally.

---

## 2. Identifiers and naming rules

| Identifier | Format | Example | Notes |
|---|---|---|---|
| `DEVICE_ID` | `^[A-Z0-9]{2,16}-[0-9]{4}$` | `PANEL-0001` | Uppercase, one hyphen, 4-digit serial. No spaces, `/`, `+`, `#` or wildcards. |
| `CH` | integer `1` or `2` | `1` | Channel number. Any other value is invalid. |
| `cmd_id` | UUID v4 string | `8f14e45f-ceea-467a-9a5a-0d6a0f0b1234` | Generated by the backend. Unique for every command, including retries. |
| `event_id` | UUID v4 string | `3b241101-e2bb-4255-8caf-4136c566a962` | Generated by the device, unique per event. |
| `boot_id` | short random string, max 32 chars | `7f3a91c2` | Optional. Generated once per device boot. Helps de-duplicate buffered data. |
| `seq` | integer ≥ 0 | `1043` | Optional. Increments per telemetry message for the lifetime of a boot. |

Topic prefix: `panel/`. Topic levels are case-sensitive. Consumers MUST NOT use wildcards when publishing.

## 3. Common conventions

1. **Encoding:** one UTF-8 JSON object per MQTT message. No JSON arrays at the top level. No comments. Newlines are allowed but not required.
2. **Timestamp `ts`:** Unix epoch time in **seconds**, UTC. Fractional seconds are allowed for millisecond precision. The device must never publish `NaN`, `Infinity` or a negative timestamp.
3. **Numbers:** JSON numbers only. `"231.4"` (string) is invalid. Booleans are JSON `true`/`false`, never `1`/`0` or `"true"`.
4. **Units:**

   | Field | Unit | Meaning |
   |---|---|---|
   | `v` | volts (V) | RMS line voltage measured by PZEM |
   | `i` | amperes (A) | RMS current measured by PZEM |
   | `p` | watts (W) | Active power measured by PZEM |
   | `e_kwh` | kilowatt-hours (kWh) | Cumulative energy counter reported by PZEM |
   | `pf` | dimensionless 0.00–1.00 | Power factor measured by PZEM |
   | `f` | hertz (Hz) | Line frequency measured by PZEM |
   | `s` | volt-amperes (VA) | Apparent power, calculated as `v × i` |
   | `q` | volt-amperes reactive (VAr) | Reactive power, calculated as `sqrt(max(s² − p², 0))` |

5. **Measured vs calculated:** the device publishes only measured fields (`v`, `i`, `p`, `e_kwh`, `pf`, `f`). `s` and `q` are calculated by the backend/dashboard and MUST be labelled as calculated in the UI. Do not send `s`/`q` from the device in version 1.
6. **Schema version:** optional integer field `"schema"` (not `v`, which is voltage). Missing means version `1`. A consumer must reject a message whose `schema` value it does not support rather than guessing.
7. **Unknown fields:** consumers MUST ignore unknown fields (forward compatibility). Publishers MUST NOT reuse a known field name with a different meaning.
8. **Missing/invalid required fields:** reject the entire message. Do not persist partially valid telemetry. Do not act on a partially valid command.
9. **Size limit:** broker enforces 16 KiB per message; application messages should stay below 1 KiB.
10. **Retained messages:** only `status` is retained. Telemetry, events, commands and acknowledgements are never retained, because stale live data must not look current after a reconnect.

## 4. Topic map

`{DEVICE_ID}` is replaced literally, for example `panel/PANEL-0001/telemetry/1`.

| Topic | Publisher → subscriber | QoS | Retain | Purpose |
|---|---|---|---|---|
| `panel/{DEVICE_ID}/telemetry/{CH}` | device → backend | 1 | no | One electrical reading for one channel |
| `panel/{DEVICE_ID}/status` | device → backend | 1 | **yes** | Online state, firmware, health; also the Last Will payload |
| `panel/{DEVICE_ID}/event` | device → backend | 1 | no | Faults, trips, lockouts, identification, state changes |
| `panel/{DEVICE_ID}/cmd` | backend → device | 1 | no | Authorized relay command |
| `panel/{DEVICE_ID}/ack` | device → backend | 1 | no | Result of a command |

Reserved for future use (NOT implemented in the MVP; do not publish to them yet):

- `panel/{DEVICE_ID}/config` — device configuration sync
- `panel/{DEVICE_ID}/schedule` — local schedule sync

## 5. Telemetry — `panel/{DEVICE_ID}/telemetry/{CH}`

### 5.1 Required fields

| Field | Type | Validation | Notes |
|---|---|---|---|
| `ts` | number | `> 0`, finite | UTC epoch seconds |
| `ch` | integer | `1` or `2` | Must match the `{CH}` topic level |
| `v` | number | `0 ≤ v ≤ 300` | Volts RMS |
| `i` | number | `0 ≤ i ≤ 100` | Amperes RMS; upper bound depends on PZEM variant |
| `p` | number | `0 ≤ p ≤ 25000` | Watts |
| `e_kwh` | number | `0 ≤ e_kwh ≤ 10 000 000` | Cumulative kWh |
| `pf` | number | `0 ≤ pf ≤ 1` | Power factor |
| `f` | number | `40 ≤ f ≤ 70` | Hertz |
| `relay` | boolean | `true` / `false` | Commanded relay state (see §5.4) |
| `state` | string | enum in §5.3 | Channel state at publish time |
| `buffered` | boolean | `true` / `false` | `true` if replayed from offline buffer |

### 5.2 Optional fields

| Field | Type | Purpose |
|---|---|---|
| `schema` | integer | Contract schema version (default `1`) |
| `boot_id` | string | Boot identifier for de-duplication |
| `seq` | integer ≥ 0 | Monotonic message counter for this boot |
| `clock_synced` | boolean | `false` if the device clock is not NTP-synchronised |

> The bounds in §5.1 are **ingestion sanity limits**, not protection thresholds. Actual protection thresholds are configured per channel from the load nameplate and must be confirmed by the project owner (see `docs/hardware_notes.md` once created). A reading inside these sanity bounds can still be unsafe for a particular load.

### 5.3 Allowed `state` values (device-reported)

| State | Meaning |
|---|---|
| `OFF` | Relay commanded open; no load current expected |
| `STARTING` | Relay closed; startup/inrush blanking window active |
| `RUNNING` | Relay closed; normal monitoring |
| `TRIPPED` | Protection opened the relay; retry or manual reset pending |
| `RETRY_WAIT` | Waiting for the configured retry delay |
| `LOCKED_OUT` | Three-strike lockout active; manual reset required |
| `METER_FAULT` | Meter unavailable/invalid; relay forced OFF |

Backend-side states (`UNKNOWN`, `STALE`, `OFFLINE`) are **not** device states and must not appear in this field.

### 5.4 Meaning of `relay` (important limitation)

The SSR-40DA has **no auxiliary feedback contact**. Therefore `relay` means:

> "The state the device has commanded and believes it is maintaining."

It is **not** proof that the physical contact is closed. The dashboard must label it as a commanded state, not a verified one. If a feedback method is added later, this field must be renamed or supplemented, never silently redefined.

### 5.5 Example

```json
{
  "schema": 1,
  "ts": 1767000000.482,
  "ch": 1,
  "boot_id": "7f3a91c2",
  "seq": 1043,
  "v": 231.4,
  "i": 1.82,
  "p": 410.2,
  "e_kwh": 12.345,
  "pf": 0.97,
  "f": 50.0,
  "relay": true,
  "state": "RUNNING",
  "buffered": false,
  "clock_synced": true
}
```

### 5.6 Cadence

Normal operation: one message per channel every 1–2 seconds. The backend marks a channel `STALE` when no telemetry arrives for 10 seconds (configurable), and the device itself treats meter readings older than a configured limit as invalid.

## 6. Device status — `panel/{DEVICE_ID}/status`

Published retained at connect and on meaningful changes; a Last Will message is configured before connecting so an unexpected disconnect is visible immediately.

### 6.1 Online payload

| Field | Type | Required | Notes |
|---|---|---|---|
| `ts` | number | yes | UTC epoch seconds |
| `online` | boolean | yes | `true` |
| `device_id` | string | yes | Must equal the topic's `{DEVICE_ID}` |
| `fw` | string | yes | Firmware version, e.g. `0.1.0` |
| `uptime_s` | integer | no | Seconds since boot |
| `rssi` | integer | no | Wi-Fi signal strength in dBm |
| `free_heap` | integer | no | Free heap bytes |
| `buffer_depth` | integer | no | Buffered telemetry messages waiting to upload |
| `dropped_total` | integer | no | Buffered messages dropped due to buffer overflow |
| `time_synced` | boolean | no | Device clock confidence |
| `channels` | array | no | `[{"ch":1,"relay":true,"state":"RUNNING"}]` |
| `reason` | string | no | Why the status was published, e.g. `boot`, `periodic`, `config` |

```json
{
  "schema": 1,
  "ts": 1767000001,
  "online": true,
  "device_id": "PANEL-0001",
  "fw": "0.1.0",
  "uptime_s": 842,
  "rssi": -58,
  "free_heap": 182344,
  "buffer_depth": 0,
  "dropped_total": 0,
  "time_synced": true,
  "channels": [
    {"ch": 1, "relay": true, "state": "RUNNING"},
    {"ch": 2, "relay": false, "state": "OFF"}
  ],
  "reason": "periodic"
}
```

### 6.2 Last Will payload (offline)

The will payload is fixed at connect time and cannot contain a real timestamp. Backend rule: an `online:false` status is authoritative regardless of its `ts`.

```json
{
  "schema": 1,
  "ts": 0,
  "online": false,
  "device_id": "PANEL-0001",
  "fw": "0.1.0",
  "reason": "lwt"
}
```

Backend also marks the device offline if no status or telemetry has arrived for 15 seconds, so a missed Last Will is not the only detection path.

## 7. Events — `panel/{DEVICE_ID}/event`

One JSON object per event. Not retained. Duplicate `event_id` values are ignored by the backend.

| Field | Type | Required | Notes |
|---|---|---|---|
| `ts` | number | yes | UTC epoch seconds |
| `event_id` | string | yes | UUID v4 |
| `type` | string | yes | Enum in §7.1 |
| `severity` | string | yes | `info`, `warning` or `critical` |
| `ch` | integer or `null` | yes | `1`, `2`, or `null` for device-level events |
| `message` | string | yes | Short human-readable description, max 200 chars |
| `data` | object | no | Structured details (rule name, measured value, threshold, `cmd_id`, …) |

### 7.1 Event types

| `type` | Typical severity | Meaning |
|---|---|---|
| `DEVICE_BOOT` | info | Device started; safe startup begun |
| `CONFIG_APPLIED` | info | Configuration accepted and validated |
| `PROTECTION_TRIP` | critical | A protection rule opened the relay |
| `PROTECTION_CLEARED` | info | Fault condition no longer present |
| `RETRY_SCHEDULED` | warning | Automatic retry scheduled after a trip |
| `LOCKOUT_ENTERED` | critical | Three-strike lockout entered |
| `LOCKOUT_CLEARED` | warning | Lockout cleared by an authorized manual reset |
| `METER_COMM_FAILURE` | critical | PZEM communication failed |
| `METER_COMM_RESTORED` | info | PZEM communication restored |
| `STALE_DATA` | warning | Readings missing or too old to trust |
| `RELAY_FAULT` | critical | Relay command/state inconsistency detected |
| `CMD_REJECTED` | warning | A command was refused; `data.cmd_id` and `data.reason` required |
| `SCHEDULE_TRIGGERED` | info | A local schedule changed a relay state |
| `LOAD_IDENTIFIED` | info | Load fingerprint matched a learned profile |
| `LOAD_AMBIGUOUS` | warning | Match confidence too low; manual confirmation needed |

AI anomaly results and health scores are **backend advisory data**. They are exposed through REST/WebSocket and stored in the database; they are not device events and must not be published on this topic by the device.

Example:

```json
{
  "schema": 1,
  "ts": 1767000123.2,
  "event_id": "3b241101-e2bb-4255-8caf-4136c566a962",
  "type": "PROTECTION_TRIP",
  "severity": "critical",
  "ch": 1,
  "message": "Overcurrent trip: 9.4 A exceeded 8.0 A limit",
  "data": {
    "rule": "OVERCURRENT",
    "measured": 9.4,
    "threshold": 8.0,
    "strike": 1,
    "relay": false
  }
}
```

## 8. Commands — `panel/{DEVICE_ID}/cmd`

Backend → device. Published only after the backend has authenticated the user, checked device ownership, validated the payload and confirmed the channel exists.

| Field | Type | Required | Validation |
|---|---|---|---|
| `cmd_id` | string | yes | UUID v4 format, 36 chars |
| `ch` | integer | yes | `1` or `2` |
| `action` | string | yes | `ON` or `OFF` (uppercase) |
| `issued_at` | number | yes | UTC epoch seconds |
| `expires_at` | number | yes | UTC epoch seconds, `> issued_at` |
| `source` | string | yes | `user`, `schedule`, `system` or `optimization` |

```json
{
  "schema": 1,
  "cmd_id": "8f14e45f-ceea-467a-9a5a-0d6a0f0b1234",
  "ch": 1,
  "action": "ON",
  "issued_at": 1767000200,
  "expires_at": 1767000210,
  "source": "user"
}
```

### 8.1 Device validation order (all must pass)

1. Valid JSON object and known schema version.
2. `cmd_id`, `ch`, `action`, `issued_at`, `expires_at`, `source` present with correct types.
3. `ch` exists on this device.
4. `action` is exactly `ON` or `OFF`.
5. Command has not expired (`now <= expires_at`, allowing a small clock-skew tolerance).
6. Duplicate check: if `cmd_id` was already processed, re-send the stored acknowledgement and **do not actuate again**.
7. Safety check: `LOCKED_OUT`, an unresolved trip, `METER_FAULT`, invalid/stale readings, or a missing meter reading all forbid `ON`.
8. Apply the command, read back the state-machine result, publish an acknowledgement, and log a `CMD_REJECTED` event if refused.

The device MUST NOT accept a command merely because it arrived on the command topic. MQTT access control is not authorization.

### 8.2 Default command lifetime

`expires_at = issued_at + 10 seconds` (configurable). A device that receives an expired command replies `REJECTED` / `CMD_EXPIRED` and does not actuate.

## 9. Acknowledgements — `panel/{DEVICE_ID}/ack`

| Field | Type | Required | Notes |
|---|---|---|---|
| `cmd_id` | string | yes | Echo of the command |
| `ch` | integer | yes | Echo of the command channel |
| `result` | string | yes | `DONE`, `REJECTED` or `FAILED` |
| `reason` | string | yes | Code from §9.1 (`OK` for `DONE`) |
| `relay` | boolean | yes | Commanded relay state **after** processing |
| `state` | string | yes | Channel state after processing (§5.3) |
| `ts` | number | yes | UTC epoch seconds |

```json
{
  "schema": 1,
  "cmd_id": "8f14e45f-ceea-467a-9a5a-0d6a0f0b1234",
  "ch": 1,
  "result": "DONE",
  "reason": "OK",
  "relay": true,
  "state": "STARTING",
  "ts": 1767000200.4
}
```

### 9.1 Result and reason codes

| `result` | `reason` | Meaning |
|---|---|---|
| `DONE` | `OK` | Requested state reached (as known to the device) |
| `REJECTED` | `SAFETY_LOCKOUT` | Lockout active; manual reset required |
| `REJECTED` | `ACTIVE_FAULT` | Unresolved protection fault |
| `REJECTED` | `INVALID_CHANNEL` | Channel does not exist |
| `REJECTED` | `INVALID_ACTION` | Action not `ON`/`OFF` |
| `REJECTED` | `INVALID_PAYLOAD` | Missing/invalid field or unsupported schema version |
| `REJECTED` | `CMD_EXPIRED` | Command arrived after `expires_at` |
| `REJECTED` | `DUPLICATE_CMD` | Already processed; cached result re-sent |
| `REJECTED` | `METER_FAULT` | Meter unavailable or readings invalid/stale |
| `FAILED` | `RELAY_READBACK_MISMATCH` | Actuation attempted but state machine disagrees |
| `FAILED` | `INTERNAL_ERROR` | Unexpected device error |

### 9.2 Command lifecycle (backend and dashboard)

| Dashboard state | Trigger |
|---|---|
| `PENDING` | Command published, no acknowledgement yet |
| `DONE` | Ack with `result: DONE` |
| `REJECTED` | Ack with `result: REJECTED` (show `reason`) |
| `FAILED` | Ack with `result: FAILED` (show `reason`) |
| `TIMED_OUT` | No ack within the configured timeout (default 5 s); **relay state remains unconfirmed*** |

\* A timeout does not prove the relay did not switch. The dashboard must reconcile with subsequent telemetry and show "unconfirmed" until telemetry confirms the physical commanded state. The requested state must never be rendered as confirmed before an ack or telemetry confirmation.

Late acknowledgements are still accepted and update the command record. Duplicate acknowledgements are idempotent: the first result is kept, later identical acks are ignored.

## 10. Offline buffering and de-duplication

1. When the broker is unreachable, the device buffers telemetry (RAM and/or flash as hardware allows) with the **original** `ts` and `buffered: true` at upload time.
2. Commands are **never** buffered or replayed after reconnect.
3. Schedules run locally and are not queued as commands.
4. Buffered telemetry is published oldest-first after reconnect, at a rate that does not starve live readings.
5. Buffer limits and drop policy are device configuration. Dropped messages increment `dropped_total` and are reported in `status`. The system must expose this loss rather than hide it.
6. Backend de-duplication key:
   - primary: `(device_id, ch, boot_id, seq)` when both optional fields are present;
   - fallback: `(device_id, ch, ts)`.
   Duplicate uploads must be stored once, not counted twice.
7. Backend must reject telemetry with a future timestamp beyond a configurable tolerance (default 5 minutes) as invalid/suspect.

## 11. Safety precedence (mandatory)

Control authority, highest first:

1. Active protection fault or lockout (device-local, deterministic).
2. Schedule rules, subject to safety.
3. Authorized user command, subject to safety.
4. Approved optimization rules, subject to safety.
5. AI advisory only.

Consequences for this contract:

- No MQTT message can clear a lockout. Manual reset is a separate authenticated action with an explicit audit event.
- A `DONE` acknowledgement means the device accepted the command **within its safety state**, not that safety was bypassed.
- `ON` is refused whenever reading validity cannot be established.
- AI output must never be translated into an `ON` command or into a tripped relay being re-closed.

### 12.1 Development (current)

- Broker: `eclipse-mosquitto:2.0.22` in Docker.
- Reachable at `127.0.0.1:1883` only (host loopback binding).
- Anonymous access allowed, **local development only**.
- Persistence enabled in the named volume `smart-panel-mosquitto-data`.
- No TLS. No usernames/passwords.

### 12.2 Deployment plan (not yet implemented)

- `allow_anonymous false`, `password_file`, one user per device plus a backend user.
- Topic ACL matrix:

  | Principal | Publish | Subscribe |
  |---|---|---|
  | device `PANEL-0001` | `panel/PANEL-0001/telemetry/#`, `.../status`, `.../event`, `.../ack` | `panel/PANEL-0001/cmd` |
  | backend | `panel/+/cmd` | `panel/+/telemetry/#`, `panel/+/status`, `panel/+/event`, `panel/+/ack` |

- TLS required before any non-local deployment.
- The dashboard never connects directly to MQTT; it uses the backend REST API and WebSocket.

## 13. Invalid-message handling

| Situation | Device behaviour | Backend behaviour |
|---|---|---|
| Telemetry invalid (type/range/enum) | must not publish it | discard, log with reason, increment reject counter; do not store |
| Telemetry `ch` ≠ topic channel | must not publish it | discard |
| Duplicate telemetry | — | ignore by de-duplication key |
| Event invalid | must not publish it | discard and log |
| Duplicate `event_id` | — | ignore |
| Command malformed, `cmd_id` present | reply `REJECTED`/`INVALID_PAYLOAD`; do not actuate | mark command `FAILED` validation (should not have been published) |
| Command malformed, no usable `cmd_id` | ignore; log locally | n/a |
| Unknown schema version | ignore; log `CMD_REJECTED` if ackable | alert; do not guess |
| Ack for unknown `cmd_id` | n/a | log and ignore |
| Ack reason unknown to backend | n/a | store raw, display as unknown, keep command unconfirmed |

Validation must never be "fixed" by widening a type check or disabling a rule to make a test pass.

## 14. Change control

- **Additive optional fields** may be introduced within contract version 1; consumers must already ignore unknown fields.
- **Changing a topic name, field name, field meaning, required field, enum value or validation rule** requires:
  1. a contract version increment,
  2. updates to this document,
  3. simultaneous updates to firmware, simulator, backend, dashboard and tests,
  4. a migration note for stored data.
- New event types are additive but must be documented here first.
- Never rename a persisted field without a database migration.

## 15. Valid and invalid examples (test fixtures)

Valid telemetry:

```json
{"ts":1767000001,"ch":2,"v":230.1,"i":0.36,"p":82.8,"e_kwh":3.02,"pf":0.99,"f":50.01,"relay":true,"state":"RUNNING","buffered":false}
```

Invalid telemetry (reject):

```json
{"ts":1767000001,"ch":3,"v":230.1,"i":0.36,"p":82.8,"e_kwh":3.02,"pf":0.99,"f":50.01,"relay":true,"state":"RUNNING","buffered":false}
```
Reason: channel `3` is not valid.

```json
{"ts":1767000001,"ch":1,"v":"231.4","i":1.82,"p":410.2,"e_kwh":12.3,"pf":0.97,"f":50,"relay":true,"state":"RUNNING","buffered":false}
```
Reason: `v` is a string.

```json
{"ts":1767000001,"ch":1,"v":231.4,"i":1.82,"p":410.2,"e_kwh":12.3,"pf":0.97,"f":50,"relay":1,"state":"RUNNING","buffered":false}
```
Reason: `relay` must be a JSON boolean.

Invalid command:

```json
{"cmd_id":"not-a-uuid","ch":1,"action":"on","issued_at":1767000200,"expires_at":1767000210,"source":"user"}
```
Reasons: invalid `cmd_id`, lowercase action.

Valid rejection acknowledgement:

```json
{"cmd_id":"8f14e45f-ceea-467a-9a5a-0d6a0f0b1234","ch":1,"result":"REJECTED","reason":"SAFETY_LOCKOUT","relay":false,"state":"LOCKED_OUT","ts":1767000201}
```

## 16. Open questions (must be resolved before firmware integration)

1. **PZEM-004T V4 variant and register map:** does the installed meter report frequency and power factor? V4 firmware revisions differ. Verify with a real read before relying on `f` and `pf` for protection.
2. **Two meters, one address:** both PZEMs typically default to Modbus address `0xF8`. Distinct addresses or two UARTs must be confirmed from the actual wiring.
3. **Offline clock:** without internet, the ESP32 has no reliable wall clock for `ts` and local schedules. Decide whether to add an RTC module, use a gateway-provided time, or mark timestamps as device-relative when `clock_synced` is false.
4. **Relay feedback:** no auxiliary contact exists on the SSR. Confirm whether any feedback (e.g. current-presence check) will be used as a secondary confirmation method.
5. **Energy counter reset policy:** PZEM `e_kwh` is cumulative and may be reset. Decide how the backend handles counter resets without corrupting per-load energy totals.
6. **Retained status on broker restart:** persistence is enabled; verify after a broker restart that only the latest status is retained and stale telemetry does not reappear.
